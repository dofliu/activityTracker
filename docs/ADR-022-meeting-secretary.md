# ADR-022：會議秘書——先接會後逐字稿，不碰即時音訊

- 狀態：**Proposed**（2026-09-08 起草；未實作。使用者確認範圍後才開工）
- 關聯：[ADR-001](ADR-001-p2-5-trust-boundary.md) 本機優先邊界、[ADR-007](ADR-007-proposal-only-secretary.md) proposal-only 秘書、[ADR-009](ADR-009-deskrag-worker-index-lifecycle.md) DeskRAG 索引生命週期、[ADR-012](ADR-012-secretary-memory.md) 記憶區（觀察可刪、有 TTL）、[ADR-015](ADR-015-local-calendar-source.md) 行事曆採集、[ADR-016](ADR-016-acceptance-center.md) 驗收中心

## Context

使用者在一場線上會議中問小秘書：「我現在在線上會議，你可以看到嗎？」秘書答「無法直接看到或聽取」，並建議把 Live Captions 貼進對話框。回答是對的：秘書目前只看得到你貼給它的文字。使用者接著問——

> 真的是一個小秘書，知道我在開會，就可以做即時紀錄、翻譯、筆記等工作？

「知道你在開會」與「幫你記」是兩件事，材料與風險完全不同：

| | 材料在哪 | 風險 |
| :-- | :-- | :-- |
| 知道你在開會 | 行事曆事件（ADR-015，`calendar_events`）＋前景視窗是 Teams（`window_events`，category 已歸 Comm） | 無：都是既有、只關於你自己的資料 |
| 會後紀錄／摘要／待辦 | Teams 自己產生的**逐字稿檔**（開啟轉錄的會議可下載 .docx／.vtt，通常落在 OneDrive） | 中：檔案裡有**其他與會者的話**；摘要需要 LLM |
| 即時字幕／翻譯 | 系統音訊（Windows WASAPI loopback）→ 本機 Whisper → 每幾秒一次 LLM | 高：**錄下其他人的聲音**；即時翻譯用雲端等於把別人的話逐段送出去 |

### 「能否改變決策」檢驗（同 ADR-015）

| 問題 | 沒有會議秘書 | 有第一層（會後逐字稿） |
| :-- | :-- | :-- |
| 會後我答應了什麼？ | 憑記憶，或自己翻逐字稿 | 秘書列出「候選待辦」，你勾了才成為未結事項 |
| 上次跟這群人談到哪？ | 找不到 | 逐字稿進知識庫，對話框直接問「上次會議關於 X 的結論」 |
| 這週開會花了多少、產出什麼？ | 問候卡只有「開了 N 場會」 | 每場會有一則可回溯的觀察，週回顧能對照「說的 vs 做的」 |

三題都會改變行為 → **第一層納入**。第三層（即時音訊）三題都不需要它才能回答 → **本 ADR 不做**，只寫下若要做必須過的門。

## Decision

### D1 分兩層；本 ADR 只決定第一層

**第一層＝會後逐字稿併入**：使用者把 Teams 匯出的逐字稿放進（或 OneDrive 同步到）一個指定資料夾，秘書把它併入知識庫與記憶區，並產出摘要與候選待辦。**不碰音訊、不錄任何人、不連 Teams／Graph API。**

**第二層＝即時字幕／翻譯**：另案 ADR。先寫下不可妥協的門（見 D6），現在不實作。

### D2 「知道你在開會」是確定性訊號，不是推測

`meeting_context()`（新增於 `core/secretary_packs.py` 或獨立模組）只回答一個布林與兩個引用：**現在有沒有正在進行的行事曆事件**（`calendar_events.instance_start ≤ now < instance_end`），以及**近 N 分鐘前景視窗是否為 Teams／Zoom／Meet**（`window_events.app_name`）。兩者都有才算「在開會」；只有一個時如實說「行事曆說在開會，但沒看到會議軟體在前景」。不從標題猜會議主題。

用途只有兩個：01 桌面在會議中多一行「📞 會議中：<行事曆標題>（還剩 M 分）」，以及**會後**（事件結束後 15 分內）若指定資料夾沒有新逐字稿，提一張 `meeting_transcript_missing` 提案：「剛結束的會議沒有逐字稿；若有開轉錄，從 Teams 下載到 <資料夾> 我就會整理」。不做會前提醒（ADR-015 已決定）。

### D3 逐字稿只從一個資料夾進來，且走既有的索引路徑

- 新設定 `meetings.transcript_dir`（預設空＝停用，與 `calendar_watcher` 同一種「沒設路徑就是關」）。只接受 `.vtt`／`.docx`／`.txt`／`.md`；**`.vtt` 目前不在 DeskRAG 的支援清單**（`rag/config.py` 只有 .pdf/.docx/…/.txt/.md 等），需新增一個 WebVTT parser：去掉 cue 編號與時間戳、保留講者標記與句子，其餘交給既有 chunker。
- 這個資料夾以 `source_domain: meeting` 加進 RAG 資料夾清單，索引由既有的 `rag.index_worker` 工作跑（ADR-009 §1：主服務不解析檔案）。刪掉檔案 → 下次掃描既有的移除路徑會拿掉切片。**不新增資料表**；一場會議的紀錄＝一個 RAG 文件＋一則記憶區觀察。
- 檔案與行事曆事件的配對只用**時間**（檔案修改時間落在事件結束後 6 小時內，取最近的一場）；配不到就用檔名，並在觀察裡明寫「未配對到行事曆事件」。

### D4 摘要是 LLM 產出，所以要有門、有收據、可刪

- 每個新逐字稿由 L0 排程 template `meeting_notes`（沿用 `daily_digest` 的形狀：`SCHEDULABLE_TEMPLATES`、收據欄位、逾時）產出**一則**觀察 `meeting:<檔案 sha1>`：三到五句摘要＋「候選待辦」清單＋「未配對／逐字稿不完整」等如實標記。同一檔案同一則（`source_ref` 去重，ADR-012），觀察可一鍵刪除、隨 TTL 過期。
- 摘要走 `synthesizer.micro_summarizer` 同一條 LLM 路徑（provider 由 `meetings.provider` 指定，**預設 `ollama`**）。逐字稿含他人發言，**選雲端 provider 時 UI 與 config 都要明說「這會把與會者的話送到 <provider>」**，並且沿用 ADR-012 邊界：prompt 與回應原文不落地，只存摘要。
- **候選待辦不是待辦**。它們出現在該場會議的提案卡上（`meeting_followups`，L0），每一條旁邊是「加入未結事項」「忽略」；沒被你點的不進 `open_loops`、不進週回顧的計數。這是「不從資料推斷意圖」原則在會議上的形狀：秘書可以說「你好像答應了 X」，但只有你能讓它成為承諾。
- 摘要句子裡出現逐字稿沒有的數字或人名 → 整段丟掉、退回「摘要失敗，逐字稿已進知識庫」（沿用問候卡的事實閘思路）。

### D5 邊界：這一層不做的事

- 不錄音、不截圖、不讀 Teams 視窗內容、不呼叫 Microsoft Graph／Teams API、不保管任何雲端憑證。
- 不自動下載逐字稿——Teams 的匯出是你的動作；秘書只等檔案落地。
- 不保存與會者名單（逐字稿裡的講者標記留在 RAG 切片裡供檢索，但觀察與提案卡只寫「N 位講者」）。
- 不做會前提醒、不評價會議、不從逐字稿推測情緒或優先順序。
- 逐字稿不進其他任何 LLM 呼叫（每日工作誌、問候卡潤飾都不讀它）；問候卡的「開了 N 場會」維持只算行事曆。

### D6 第二層（即時音訊）若要做，必須過的門——現在不做

1. 預設關閉；開啟需要 execution token，與 L2 執行器同一道門（ADR-008）。
2. 只在你**明確按下**「開始記錄」時開始，畫面全程有明顯的「● 錄音中」，會議結束或你按停就停；沒有「自動偵測到會議就錄」。
3. 語音轉文字**只用本機模型**（whisper.cpp／faster-whisper），音訊不落地（只留文字）。
4. 即時翻譯若用雲端 provider，每次開啟都要再確認一次，而且逐字稿觀察要標明「內容曾送往 <provider>」。
5. 另一份 ADR、另一輪驗收；本 ADR 的 A22 不涵蓋它。

## Alternatives considered

- **Microsoft Graph／Teams 會議 API 直接拿轉錄**：需要 OAuth、租戶管理員同意、保管 refresh token；違背 ADR-001 本機優先，且對個人帳號多半拿不到。**不做**。
- **Teams bot 入會**：等於一個第三方參與者，所有與會者都會看到；不是個人秘書的形狀。**不做**。
- **繼續用「貼 Live Captions 到對話框」**：今天就能用，秘書當天也這樣建議了；但字幕不會自己存檔、貼上的內容不進記憶區。第一層把它變成可回溯的紀錄，不取代它。
- **系統音訊 + 本機 Whisper 一次做到即時**：技術可行，但風險層級不同（D6），且第一層還沒證明「會議紀錄進記憶區」值得。**先做第一層用兩週再說**。

## Acceptance criteria（實作時對應 TODO A22）

1. 把一個 Teams 匯出的 `.vtt` 與一個 `.docx` 放進 `meetings.transcript_dir`，下一次 `meeting_notes` 執行後：知識庫可檢索到內容、記憶區有一則 `meeting:<sha1>` 觀察（摘要＋候選待辦＋配對到的行事曆標題或「未配對」）、01 有一張 `meeting_followups` 提案。
2. 候選待辦按「加入未結事項」才出現在 `open_loops`；沒點的不進任何計數。
3. `meetings.provider` 為 `ollama` 時，全程無對外連線；改為雲端 provider 時，設定頁與提案卡都明示內容會送往該供應商。
4. 刪掉觀察→ 立即消失；刪掉檔案→ 下次掃描切片消失；兩者都不影響行事曆與其他資料。
5. 行事曆事件進行中且 Teams 在前景 → 桌面出現「會議中」一行；只有其一 → 文字如實說明差異；事件結束 15 分後無新檔 → `meeting_transcript_missing` 提案出現一次，有檔就不出現。
6. 契約測試：WebVTT parser（cue／時間戳／講者標記）、時間配對邊界、候選待辦不自動成為 open loop、雲端 provider 的明示文案、觀察去重與可刪。

## Consequences

- 秘書從「只看你做了什麼」多了「你答應了什麼」的一個來源，而且是你能刪、能改、能忽略的形狀。
- 代價：多一個 LLM 呼叫點（預設本機）、一個 WebVTT parser、一個資料夾設定、一個 L0 template、兩種新提案類型；沒有新資料表、沒有新採集器程序（配對只讀既有兩張表）。
- 最大的不確定性是 Teams 匯出的檔案形狀（.docx 內的講者／時間排版、.vtt 的 `<v 講者>` 標記）——實作時以真實匯出檔當測試夾具，解析不了的檔案進 `degraded_sources` 如實列出，不猜。
