# ADR-031：`omni demo` 示範資料集的邊界

- 狀態：**Accepted**（2026-09-22 起草，TODO E1；實作留待下一輪，本 ADR 只定邊界）
- 關聯：[core/runtime_paths.py](../core/runtime_paths.py)（`OMNICONTEXT_HOME` 覆寫）、[ADR-016](ADR-016-acceptance-center.md) 驗收中心、[ADR-019](ADR-019-secretary-desk-home.md) 秘書桌面、[ADR-001](ADR-001-p2-5-trust-boundary.md) 本機優先與信任邊界
- 依據：[ROADMAP.md §14](../ROADMAP.md)、[docs/TODO.md](TODO.md) E1

## Context

任何一個全新環境打開儀表板都是空的——沒有活動、沒有提案、沒有記憶、沒有 Handoff。
這不只是展示不好看：**它讓大部分功能只能靠 831 項 contract test 證明存在，沒有人能在五分鐘內
親眼看一次**。每一個雲端開發 session 也是同一個問題的另一面——容器裡沒有真實使用者資料，
排查一個「01 首頁挑錯焦點」之類的 bug，得自己手動塞事件進資料庫才看得到畫面。

`omni demo` 要解決的正是這個落差：一份匿名化、可公開的假 transcript ＋ Git ＋ 檔案事件，
一個指令灌進去，五分鐘看到首頁、提案與 Handoff。

但這個專案有一條比「好展示」更重的鐵律：**誠實文化——沒被採集到的資料不推測，每個聲明附收據**。
示範資料如果沒有邊界，會直接撞上這條鐵律最脆弱的兩個地方：

1. **驗收中心與問候卡是本專案對「這是真的」最重的承諾**（ADR-016：`evidence` 是對外契約）。
   如果示範資料能讓 A 段收據或問候卡數字變綠，等於教會這個系統說謊——而且是最不該犯的那種謊。
2. **示範資料只能污染示範資料**。使用者真實的 `OMNICONTEXT_HOME`（Windows 實機、雲端 session 的
   工作目錄）絕不能因為跑了一次 `omni demo` 而混進假的 commit 或假的 AI 對話。

## Decision

### 1. 示範資料只能寫進另開的家目錄，絕不碰使用者的 `OMNICONTEXT_HOME`

`core/runtime_paths.py` 的 `application_home()` 已經有 `OMNICONTEXT_HOME` 覆寫機制（供測試與容器
E2E 使用，見 `docs/NEXT_SESSION.md` 遠端容器環境備忘）。`omni demo` 沿用同一條路徑，不新開一條：

- 執行時**必須**指向一個新的、目前不存在或已知是示範資料的目錄（例如
  `~/.omnicontext-demo` 或使用者以 `--home` 明講的路徑），**絕不落在**
  `application_home()` 在沒有 `OMNICONTEXT_HOME` 覆寫時會解析到的預設路徑
  （原始碼 checkout 或 `~/OmniContext`）。
- 若解析出的目標目錄已存在**且不是**由上一次 `omni demo` 建立的（見第 3 點的旗標檔），
  一律 **fail-closed** 並印出實際路徑與原因，不自動覆寫、不詢問後代做主。
  「讀不到就不動手」與 ADR-009 Addendum C 的 Chroma 回收邊界是同一個原則。
- `omni demo` 的說明文字與 `--help` 輸出要明講「這會建立/清空一個獨立的示範家目錄，
  不會動到你現有的資料」。

### 2. 每一筆示範資料都要標成示範，且標記要一路傳到 API

不是「文件裡寫一句示範資料」就算數——示範旗標要進資料本身：

- 示範資料的來源事件（AI turn、commit、檔案事件）一律帶一個可回溯的 provenance 標記
  （沿用既有事件表已有的來源欄位模式，不新開一套 provenance 機制）。
- `GET /api/v1/system/status` 或等價端點在示範家目錄啟動時要回報 `demo_mode: true`；
  前端在示範模式下要有肉眼可辨的標示（例如頂欄一條顏色不同的橫幅），不能讓截圖或錄影
  誤導成「這是實機收據」。
- 驗收中心（ADR-016）與問候卡（ADR-019）在 `demo_mode: true` 時，其判定與話術**不得**
  被示範資料餵綠——具體做法留給實作 PR 決定（例如整段標成 `needs_human`／額外一句「示範模式，
  非實機收據」），但契約測試必須覆蓋這一條，這是本 ADR 唯一不可退讓的判準。

### 3. 一次性灌入，冪等，且可辨識是自己建的

- `omni demo` 重跑時，若偵測到目標目錄是自己上一次建立的示範家目錄（例如目錄下有一個
  `omni demo` 專屬的旗標檔／metadata），**清空重灌**是允許的（示範資料本來就可拋棄），
  但仍要在動手前印出「即將清空 `<path>` 並重新灌入示範資料」讓使用者看得到。
- 旗標檔本身也要能被驗收中心或啟動流程讀到，用來實作第 2 點的 `demo_mode` 判定
  ——不要用「檔案數量像示範資料」這種用猜的判斷（呼應 `docs/NEXT_SESSION.md` 已經記下的
  教訓：「東西在不在」不等於「東西有沒有內容」，這裡是反過來——不能靠猜內容像不像示範
  來判斷是不是示範，要有一個明確的、寫死的旗標）。

### 4. 匿名化的具體邊界

- 示範 transcript／commit message／檔案路徑一律是虛構內容，不得取材自本 repo 開發過程中
  任何真實對話或真實 commit（即使去識別化也不行——最簡單、最不會出錯的規則是從頭編造）。
- 示範資料**不含**任何看起來像真實金鑰、token、email 或人名的字串，避免被誤認成外洩。
- 示範專案數量與時間跨度足以讓 ADR-017（模式感知提案）、ADR-020（每週回顧）、
  ADR-019（秘書桌面）都有東西可挑（至少一個「近一週活躍」與一個「上週活躍、這週冷落」的
  專案），但不需要覆蓋 A 段全部 22 項——`omni demo` 的目的是「看得到系統長什麼樣子」，
  不是取代實機收據。

## Consequences

**好的**：

- 任何新環境（含每一個雲端開發 session）五分鐘內看得到系統真正跑起來的樣子，
  排查前端／秘書桌面／提案排序的 bug 不必再手動塞資料。
- 因為復用 `OMNICONTEXT_HOME` 既有機制，不新增第二套「家目錄在哪」的邏輯。
- `demo_mode` 旗標把「示範」與「實機」的邊界寫進資料與 API，不是只寫在文件裡——
  這正是本專案要求的「聲明要附收據」反過來用在自己身上。

**代價，如實記下**：

- 多一組資料要維護（示範 transcript／commit／檔案事件的內容本身），格式跟著
  ADR-025 的 parser 介面走，parser 改介面時示範資料要跟著檢查。
- `demo_mode` 判定要覆蓋驗收中心與問候卡兩處話術，這是這個功能裡**唯一需要動到
  既有信任邊界程式碼**的部分，實作時要格外小心不要把判定寫反（例如忘記某個字串接
  `demo_mode` 檢查，讓示範資料在漏掉的那個角落被當成真的）。
- 這個功能不會、也不打算讓 A 段任何一項變成有收據——刻意不做，理由見上方第 2 點。

## 尚未決定、留給實作 PR

- 示範資料以程式碼內建常數／fixture 檔案，還是隨套件附一份 JSON/SQL 種子檔——選哪個
  由實作時的維護成本決定，這裡不預先鎖死格式。
- `--home` 參數是否為必填，或允許不帶參數時用一個寫死的預設示範路徑（例如
  `~/.omnicontext-demo`）——同樣留給實作 PR，但預設路徑**必須**明顯不同於
  `application_home()` 的一般預設值。

## 完成判準（收據，供 TODO E1 實作那一輪核對）

- 契約測試涵蓋「示範資料不得寫進非示範家目錄」（目標路徑等於一般預設家目錄時 fail-closed）
  與「示範旗標一路標到 API」（`demo_mode: true` 且驗收中心／問候卡不把示範數字當實機收據）。
- 在乾淨容器對**新開的**示範家目錄執行 `omni demo` 後，`GET /api/v1/secretary/home` 有焦點
  與記憶、`reports/handoffs/` 有檔案；對**真實**家目錄執行時 fail-closed 並印出原因。
- `pytest` 全綠；`python main.py verify`（指向非示範家目錄時）輸出與這一輪之前相同——
  示範功能不改變任何既有判準。
